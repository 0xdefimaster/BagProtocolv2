# Phase 19.X-B.1 — Real LI.FI Caller-Compatibility Spike

## Summary

**STATUS: STILL BLOCKED — but the blocker changed shape this session, and
one of the "successes" along the way turned out to be a false positive
that was caught and is disclosed here rather than reported as evidence.**

## What's newly true this session (real, verified)

1. `web_fetch` (unlike this sandbox's `bash_tool`, which gets a `403` from
   both `li.quest` and `rpc.mainnet.chain.robinhood.com`, reconfirmed
   again this session) **can** reach `li.quest` for at least some
   requests. `GET https://li.quest/v1/chains` returned a genuine, live
   response — verified live (not a canned doc example) because per-chain
   native-ETH `priceUSD` values differ slightly across chains in a way a
   static example wouldn't, and the response's own `destination_url`/
   `final_url` metadata matched the requested URL exactly. This response
   independently confirms, straight from LI.FI's live API (not just their
   blog/docs), that Robinhood Chain is registered with `id: 4663,
   mainnet: true`, and reveals its real `diamondAddress`
   (`0xB477751B76CF82d00a686A1232f5fCD772414Af3`) and per-chain
   `permit2Proxy` (`0x8eABB4E117fB70b346592e013855f6d825F50af1`).
2. LI.FI's own docs (`docs.li.fi/api-reference/authentication`) confirm
   **no API key is required** for basic `/v1/quote` use — ruling out an
   auth-header hypothesis for the 400s described below.
3. Fetching the EXACT example quote URL from LI.FI's own official docs
   (Gnosis→Polygon USDT→USDC.e, `docs.li.fi/api-reference/authentication`)
   returned a genuine, complete, live quote — real `transactionRequest.{to,
   data, value, from, chainId, gasPrice, gasLimit}`, real per-step
   `approvalAddress`es, live fee/gas estimates. This proves the JSON shape
   this spike needs (Step 4's exact deliverable list) is real and
   fetchable **in principle**.

## What is still NOT proven — and a false positive caught mid-session

Every attempt to fetch a **new** query — same-chain Robinhood WETH→USDG,
with real, verified token addresses, a real well-known wallet address, and
a real amount — returned an HTTP 400, EXCEPT one attempt that appeared to
return HTTP 200 with a full quote. That apparent success was **not
genuine**: the returned JSON was byte-for-byte identical to the earlier
Gnosis→Polygon fetch, including its `transactionId`, and its own
`destination_url`/`final_url` metadata revealed it was actually served
for `fromChain=100&toChain=137&...` — the PREVIOUS query — not the
Robinhood Chain query just requested. `web_fetch` appears to substitute a
previously-seen response for a URL it doesn't have fresh content for,
rather than erroring, for at least this endpoint/pattern. This was caught
by checking the response's own metadata before treating it as evidence,
not assumed correct — and per this task's explicit instruction ("Do not
fake the quote... do not present a mock as real LI.FI evidence"), it is
disclosed here as a caught false positive, not used as a result.

Net effect: **no genuine, fresh, same-chain Robinhood Chain WETH/USDG LI.FI
quote was obtained this session.** Every request that WAS genuinely
attempted fresh (confirmed via matching destination_url metadata) for
that specific pair returned 400, and the tooling available cannot
distinguish "this pair truly has no live LI.FI route" from "some
parameter is wrong" without being able to read the actual 400 response
body (`web_fetch` surfaces only `CLIENT_ERROR: 400`, not LI.FI's own
error payload, which per their docs has a specific code+message that
would normally explain exactly what's wrong).
